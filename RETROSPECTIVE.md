# Ретроспектива: где AI ошибся

Ошибки, найденные и зафиксированные в `docs/plans/decisions.md` по ходу фаз 0–7. Главный паттерн: AI опирался на «общеизвестное» знание и предположения вместо проверки фактического API и негативных сценариев.

| # | Где AI ошибся | Как заметили | Какая проверка поймала бы раньше |
|---|---|---|---|
| 1 | Планировал `allure-junit5` для JUnit 6.1.3, но в Allure 3.x этот артефакт заменён на `allure-jupiter` | Сверка с Maven Central (`maven-metadata.xml`) на фазе 0 показала, что `allure-junit5` в 3.x не публикуется | Проверить наличие артефакта в Maven Central **до** планирования, а не после (правило R1) |
| 2 | Планировал `PageObject` + `@FindBy` + `@Url` + `open(Class)` по «классическому» Selenide, но в 7.18.2 их нет | `jar tf` + `javap` по реальному артефакту на фазе 2 показали отсутствие классов | Инспекция фактического API зависимости (`jar tf`/`javap`) перед выбором стиля S2, а не знание Selenide 6.x |
| 3 | Считал дефолтный каталог результатов `build/allure-results`, но Allure Java пишет в `./allure-results` | Реальный прогон + README `allure-jupiter` показали, что `build/` — это дефолт Gradle-плагина, а не библиотеки | Один прогон и проверка, куда реально легли result JSON, до фиксации путей |
| 4 | Полагал, что `@Step` работает из коробки, но без AspectJ weaver шаги не пишутся | В result JSON шаги не появились при зелёном прогоне | Проверять, что шаги есть в result JSON, а не только «тесты зелёные» |
| 5 | В Jenkins-проверке наличия JUnit XML использовал `ls ... \| head -1` — `head` возвращал свой exit code, и отсутствие XML не обнаруживалось | Прогон сценария «результатов нет» (missing-results probe) дал зелёный статус при отсутствии XML | Явно тестировать негативный сценарий и проверять exit code каждого шага пайплайна |
| 6 | Предполагал, что `withCredentials` увидит Telegram-credentials из user store, но pipeline их не видит (`CredentialNotFoundException`), нужен system scope | Сборка #3 упала на `CredentialNotFoundException`; system store → `404` | Read-only проверка области/доступности credentials до запуска сборки |
| 7 | Полагал, что Jenkins Allure plugin по умолчанию строит Allure 3, но `allureVersion` по умолчанию = 2 | Чтение документации плагина 3.0.0 | Проверять дефолтные значения конфигурации плагина по README, а не по названию версии |

## Вывод

Все ошибки одного класса: **предположение вместо проверки**. Дешёвые проверки, которые ловили бы их раньше:

- существование артефакта/класса в Maven Central или в jar (`maven-metadata.xml`, `jar tf`, `javap`);
- один фактический прогон и проверка побочных эффектов (куда легли результаты, появились ли шаги);
- явный негативный сценарий (нет результатов → сборка должна падать);
- проверка области видимости credentials и дефолтов плагинов по документации, а не по памяти.
