ЗАДАЧА ФАЗЫ 5 — уведомление в Telegram по итогам прогона в GitHub Actions.

ПРЕДУСЛОВИЯ
- Есть зелёный workflow (фаза 4), имя артефакта и URL опубликованного отчёта.
- Определись со способом: готовый action (меньше кода, зависимость от стороннего репозитория) или `curl` к Bot API (полный контроль, без сторонних action). Выбери один, обоснуй, запиши в `decisions.md`.

1. СЕКРЕТЫ
   - `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — только GitHub Secrets. В репозитории и в тексте workflow значений быть не должно.
   - Проверь, что бот добавлен в чат и `chat_id` корректный (для групп id отрицательный).
   - Не печатай секреты: никаких `echo`, `set -x`, отладки с токеном. Если токен нужен в URL — не логируй URL целиком.

2. СООБЩЕНИЕ
   - Отправляй при `success` и `failure`; при `cancelled` — не отправляй (или отдельным коротким текстом, по решению).
   - Содержимое: статус, ветка, короткий SHA, ссылка на run, ссылка на Allure-отчёт, количество упавших тестов и их имена (если извлекаются из `build/test-results/test/*.xml` или `allure-results`).
   - Формат: HTML или MarkdownV2. Помни про экранирование спецсимволов в MarkdownV2 — иначе сообщение не отправится. Для имён тестов с `[`, `_`, `.` это критично.
   - Сообщение должно быть читаемым с телефона: без простыни логов, ссылки — кликабельные.

3. УСТОЙЧИВОСТЬ
   - Если секреты не заданы (например форк/локальный репозиторий) — шаг должен аккуратно пропуститься с notice, а не уронить сборку.
   - Ограничь количество ретраев отправки; при ошибке API — короткий вывод без токена.
   - Не отправляй уведомление на каждый шаг, только один итоговый.

4. ПРОВЕРКА
   - Реальный прогон: успешный и намеренно упавший тест (временно сломай ассерт → прогон → верни).
   - Убедись, что в обоих случаях сообщение пришло и содержит правильные ссылки.
   - Проверь логи workflow на отсутствие токена (`git grep` по файлу + просмотр лога глазами).
   - Проверь, что без секретов (например в PR из форка) workflow не падает.

5. ОТЧЁТ
   - Дифф workflow.
   - Скриншот/текст сообщения (без токена).
   - Имена секретов и где они заданы.
   - Фрагмент, который переиспользуем в Jenkins (фаза 6): тот же текст, тот же формат, другой способ доставки credentials.
   - Обнови `decisions.md`: способ, имена секретов, статус фазы.

ОГРАНИЧЕНИЯ
- Не добавляй сторонние зависимости в Java-код.
- Не выводи токен и `chat_id` в лог, даже частично.
- Не коммить секреты и `.env`.

DoD ФАЗЫ
- Сообщения приходят для success и failure.
- В логах и репозитории нет токена.
- При отсутствии секретов сборка не падает.
- Шаблон сообщения переиспользуем для Jenkins.
