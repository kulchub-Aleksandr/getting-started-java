ЗАДАЧА ФАЗЫ 2 — PageObject и дополнительные тесты. TestBase и конфиг не переписывай; Allure не подключай.

ПРЕДУСЛОВИЯ
- Прочитай `decisions.md`: S2 (подход к page), S3 (где ассерты), S4 (fluent), S5 (шаги), S6 (навигация), S8 (данные), S9 (язык имён), S10 (метаданные Allure), S11 (параллельность).
- Если хотя бы S2/S3/S5 не решены — задай вопросы с дефолтами и дождись ответа. Это блокер фазы.

1. PAGE OBJECT
   - Реализуй ровно тот подход, который записан в `decisions.md`. Не смешивай стили: либо `PageObject` + `@FindBy`, либо композиция `$`/`$$`, либо компоненты.
   - Одна страница/компонент = один класс. Локаторы приватные/инкапсулированные, в тестах их быть не должно.
   - Локаторы: `data-testid`, `aria-label`, role, текст. Учитывай реальную разметку github.com — проверь в браузере, не выдумывай селекторы.
   - Ассерты — согласно S3. Если «только в тестах»: page-методы возвращают данные/`this`, проверки в тестах.
   - Fluent API — согласно S4. `@Step` — согласно S5 (если S5 = «отдельный steps», не дублируй шаги в page).
   - Навигация — согласно S6 (`page.open()` vs `open()` в тесте).
   - Имена классов/методов — согласно S1/S9, без «Page» в каждом слове, если принято иное.

2. ТЕСТЫ (добавь 2–3 к существующему)
   - Позитив: поиск существующего запроса, проверка релевантного результата.
   - Негатив: заведомо несуществующий запрос — пустая выдача/сообщение «no results». Ассерт на устойчивый признак, не на точную формулировку, которая меняется.
   - Навигация: переход в найденный репозиторий/раздел и проверка ключевого элемента.
   - Данные — согласно S8. Если параметризация не выбрана, не тащи `@ParameterizedTest`.
   - Тесты независимы: каждый открывает нужную страницу сам; порядок выполнения не важен.

3. СТАБИЛЬНОСТЬ (без хаков)
   - Никаких `Thread.sleep`, `refresh` в цикле, retry-аннотаций.
   - Ожидания — через Selenide conditions. Если элемент реально появляется асинхронно, увеличь таймаут конфигом, а не паузой.
   - Учти риск captcha/rate-limit: не делай 5 поисков подряд в одном тесте; негативный тест не должен зависеть от количества результатов.

4. ПРОВЕРКИ (часть DoD)
   - `./gradlew test -Dselenide.headless=true` — все тесты зелёные.
   - Прогони **дважды подряд** — результат стабилен.
   - `git grep -n "\[data-testid\|aria-label\|xpath\|//\*\[" -- src/test/java` (или аналог): локаторы не должны встречаться в тестовых классах.
   - `git grep -n "sleep\|Thread\." -- src/test/java`: пусто.

5. ОТЧЁТ
   - Карта страниц: класс → URL → ключевые методы/локаторы.
   - Список тестов и что каждый проверяет.
   - Найденные ограничения github.com (динамические id, A/B-разметка) и как обошли.
   - Обнови `decisions.md`: карта страниц, стратегия локаторов, известные риски флака, статус фазы.

ОГРАНИЧЕНИЯ
- Не меняй TestBase/конфиг, кроме добавления того, что требует S2–S5 (например хелпер `open`).
- Не добавляй зависимости.
- Не коммить.

DoD ФАЗЫ
- 3–4 теста, все зелёные headless, два прогона подряд.
- В тестовых классах нет локаторов и `sleep`.
- Стиль page-слоя соответствует `decisions.md` без «гибридов».
