ЗАДАЧА ФАЗЫ 6 — те же тесты и генерация отчёта, что локально и в GitHub Actions, в Jenkins: публикация JUnit XML и Allure, уведомление в Telegram, проверка на реальном агенте.

ПРЕДУСЛОВИЯ
- Прочитай `decisions.md` (раздел 3.6 и «Версии»). Записанные там факты — исходные; расхождение исправляй с причиной.
- Пока нет ответов блока 0 — не пиши `Jenkinsfile` и не меняй Jenkins.
- Job — Pipeline from SCM (`Jenkinsfile` в корне); inline — только временный probe, он не считается DoD. Зафиксируй имя job, URL и ветку.

0. УТОЧНИТЬ (стоп-блок; для каждого пункта — рекомендуемый дефолт)
   1. Доступ: URL, версия, вход (SSO/API token), права студента (создать job, credentials, запускать на агенте), VPN. Дефолт: Jenkins API token, job в своей папке.
   2. Агент: label, ОС, JDK, workspace, наличие `bash`, Node ≥ 22.18, Docker/`docker.sock`. Дефолт: `agent { label '<согласованный>' }`; JDK агенту достаточно (Gradle 9.6 требует 17+).
   3. Браузер: локальный Chrome/драйвер на агенте или remote (Selenoid/Grid). Дефолт — по `decisions.md`; remote — только если локального браузера нет или среда не воспроизводится, тогда нужны URL, credentials ID, браузеры и слоты.
   4. Credentials: точные ID для Telegram и (при remote) WebDriver URL, кто создаёт. Учесть scope: user-store credentials pipeline не видит, нужен system scope (администратор).
   5. Плагины и отчёт: версии Pipeline, JUnit, Allure, HTML Publisher, Credentials Binding, Timestamper; способ публикации (Allure plugin или CLI) и политика `FAILURE`/`UNSTABLE`. Дефолт: Allure Jenkins 3.0.0 (`allureVersion: '3'`), `UNSTABLE` не использовать.
   6. Параметры job (`BRANCH`, `BROWSER`, `HEADLESS`, `BASE_URL`): нужны ли, дефолты, кто меняет. Секретов в параметрах быть не может.
   7. Если Jenkins или агент недоступны — только статическая проверка синтаксиса; интеграция помечается непроверенной, DoD не закрыт.

УЖЕ ПРОВЕРЕНО В ЭТОМ РЕПОЗИТОРИИ (не выводи заново; при расхождении правь `decisions.md`)
- На агентах нет локального Chrome/chromedriver и `docker.sock`; целевая среда — общий Selenoid через `withCredentials`.
- `allure-jenkins-plugin` 3.0.0 по умолчанию ставит `allureVersion` = 2 — версию задавать явно; плагин вызывает свой CLI, он может отличаться от закреплённого 3.33.0.
- Allure 3: `index.html` лежит в корне output (`build/allure-report`), не в `awesome/`; `summary.json` сверять с числом тестов.
- `ls .../*.xml | head` маскирует exit code — наличие XML проверять без пайпа.
- JDK агента может отличаться от локального Java 25; версии проекта без решения не менять.

1. АРХИТЕКТУРА (обосновать в `decisions.md`)
   - Браузер — по `decisions.md`. Не поднимать Selenoid/Grid «на всякий случай» и не ставить браузер на агент без согласования.
   - Remote URL — только через `withCredentials`, тем же ключом, что локально и в GHA (`REMOTE` / `-Dselenide.remote`); в логе подтвердить, что браузер удалённый.
   - `--no-sandbox` — не универсальная настройка: только как компромисс конкретного runner, с записью причины, риска и области действия.

2. JENKINSFILE
   - Declarative, `agent { label '<согласованный>' }`, `skipDefaultCheckout` при ручном checkout.
   - Стадии: Checkout → Test → Report → Publish; уведомление — в `post`.
   - `options`: `timestamps()`, `buildDiscarder`, `disableConcurrentBuilds()`, разумный `timeout`.
   - Прогон — та же команда, что локально и в GHA: `./gradlew clean test -Dselenide.headless=true` (на Windows — `gradlew.bat`); те же `-D`/env, без отдельного «jenkins-профиля».
   - `catchError(buildResult: 'FAILURE', stageResult: 'FAILURE')` вокруг тестов, чтобы отчёт и публикация выполнились, а сборка осталась красной. `|| true`, `returnStatus` и ручной `SUCCESS` не использовать.
   - Отчёт: Allure plugin (`allureVersion: '3'`, `reportBuildPolicy: 'ALWAYS'`) или закреплённый CLI — по решению из п. 0.5. Проверить `index.html` и `summary.json`.
   - Публикация: `junit` по `build/test-results/test/*.xml`; всегда архивировать `build/allure-results/**`, `build/test-results/**`, `build/reports/**` и HTML-отчёт. Ссылка на отчёт должна открываться со страницы сборки.
   - Порядок в `post { always }`: архив → junit → allure → уведомление, чтобы падение одного шага не отменяло остальные.

3. СТАТУСЫ

| Сценарий | Ожидание |
|---|---|
| Тесты зелёные | `SUCCESS`, JUnit XML есть, отчёт открывается |
| Падение assertion | `FAILURE`, XML с упавшим тестом, вложения: скриншот и page source |
| Ошибка компиляции | `FAILURE`, XML нет, консоль и архив сохранены |
| Результатов нет | `FAILURE` или согласованное предупреждение, но не зелёный статус |

- `UNSTABLE` — только по явному решению. `post { success }`/`post { failure }` его не ловят: уведомление тогда из `always` по фактическому статусу.
- Не понижать `FAILURE` до `UNSTABLE` и не повышать `UNSTABLE` до `SUCCESS` без записи в `decisions.md`.

4. УВЕДОМЛЕНИЕ
   - Тот же `.github/scripts/notify-telegram.sh` и текст, что в фазе 5; различается только доставка credentials.
   - `withCredentials` (Secret text) для token/chat id; значения не печатать, `set -x` не включать; консоль проверить на токен, `chat_id=` и URL API.
   - Скрипт — bash: на Windows-агенте нужен `sh`/порт, это согласовать до реализации.
   - Отправка при success и failure. Без credentials — предупреждение и пропуск, сборка не падает; ошибка Telegram API не меняет статус тестов.
   - `REPORT_PUBLISHED` — по фактическому наличию отчёта; ссылка — на конкретную сборку и доступный отчёт.

5. ПРОВЕРКА НА РЕАЛЬНОМ АГЕНТЕ

| # | Сценарий | Что подтвердить |
|---|---|---|
| 1 | Success | статус, JUnit, отчёт со страницы сборки, уведомление, нет секретов |
| 2 | Падение assertion (временно, затем откат) | статус и артефакты по п. 3, вложения сохранены |
| 3 | Ошибка компиляции (временно, затем откат) | статус по п. 3, архив и уведомление не отменены |
| 4 | Нет результатов | статус по п. 3, зелёного нет |
| 5 | Повторный запуск | нет залипших сессий/портов; при remote локальный Chrome не нужен |
| 6 | Секреты | в консоли нет токена, chat id, URL с credentials |

- Jenkins недоступен — статическая проверка синтаксиса и явная пометка «интеграция не проверена», а не выдача её за DoD.

6. ОТЧЁТ
   - `Jenkinsfile` + `git diff --stat`; плагины с версиями, credentials ID (без значений), способ запуска браузера.
   - Матрица п. 5: сценарий, статус, ссылки на сборки, что сохранено.
   - Отличия от GHA и что осталось общим: команда, ключи, версия CLI.
   - Обнови `decisions.md`: архитектура, способ отчёта, плагины, credentials, политика статусов, конфигурация job (SCM URL, ветка, script path), ограничения.

ОГРАНИЧЕНИЯ
- Не устанавливать плагины, не менять глобальную конфигурацию Jenkins и не создавать credentials без разрешения.
- Не менять тесты и локаторы ради Jenkins.
- Не хранить токены, chat id и URL с credentials в `Jenkinsfile`, параметрах job и репозитории.
- Не копировать `--no-sandbox` как универсальную настройку.
- Не предполагать совместимость Allure plugin с Allure 3 без проверки.
- Не добавлять шаги «на будущее» вне DoD.

DoD ФАЗЫ
- Success и контролируемые падения дают ожидаемый статус; падение не замаскировано.
- JUnit XML опубликован; Allure-отчёт доступен из сборки; при падениях сохранены результаты, вложения и отчёт.
- Уведомление приходит при success и failure (или по согласованной политике для `UNSTABLE`).
- Секретов нет в консоли и репозитории.
- Задокументированы плагины и версии, credentials ID, способ запуска браузера, политика статусов.
- Если Jenkins или агент недоступны — интеграция помечена непроверенной, DoD не закрыт.
