ЗАДАЧА ФАЗЫ 6 — сборка в Jenkins: те же тесты и генерация отчёта, что локально и в GitHub Actions, публикация JUnit XML и Allure, уведомление в Telegram, проверка на реальном агенте.

ПРЕДУСЛОВИЯ
- Прочитай `decisions.md`: версии, команды Allure, известные ограничения Jenkins/плагинов, текущий статус фазы 6.
- Факты, уже записанные в `decisions.md` (URL Jenkins, label, Selenoid, версии), считай **гипотезами для подтверждения**, а не разрешением молча выбрать архитектуру. Расхождение — исправь `decisions.md` с причиной.
- Пока не получены ответы из блока 0, не пиши `Jenkinsfile` и не меняй Jenkins.

0. УТОЧНИТЬ ДО РЕАЛИЗАЦИИ (стоп-блок; вопросы — с рекомендуемым дефолтом)
   1. Jenkins: URL, версия, общий/личный, доступ по VPN, вход (Keycloak/SSO), способ API (Jenkins API token), права студента: создать job, читать плагины, создавать credentials, запускать на агенте.
   2. Агент: имя/хост, ОС и архитектура, label, запускается ли job на агенте или на controller, путь workspace. Проверить на агенте: `java -version`, `./gradlew --version`, `node --version`, `npx allure@3.33.0 --version`, `google-chrome --version` / `chromium --version`, `chromedriver --version`, `docker version`, наличие `docker.sock`, права (root/non-root).
   3. Браузер: есть ли Chrome/Chromium и драйвер на агенте, работают ли headless-зависимости. Приоритет — **браузер на агенте без remote-инфраструктуры**. Remote (Selenoid/Grid) — только если локального браузера нет или он не воспроизводит среду, и это отдельно согласовано; тогда уточнить URL, credentials ID, доступные браузеры и слоты.
   4. Параметры: нужны ли параметры job (`BRANCH`, `BROWSER`, `HEADLESS`, `BASE_URL`), их дефолты и кто их меняет. Параметры не должны дублировать конфиг и не могут содержать секреты.
   5. Credentials: точные ID для Telegram (token, chat id) и, если нужен remote, для WebDriver URL. Кто и где их создаёт. Не выдумывай имена и не создавай credentials через API без разрешения.
   6. Плагины: установлены ли и каких версий Pipeline, JUnit, Allure Jenkins (`allure-jenkins-plugin`), HTML Publisher, Credentials Binding, Timestamper, Build Discarder. **Ничего не устанавливать и не менять глобально без явного разрешения**; при отсутствии плагина — согласованный fallback и запись ограничения.
   7. Публикация отчёта: закреплённый CLI (как локально и в GHA) или Allure Jenkins plugin. Для плагина нужна доказанная совместимость с Allure 3 и фактическая версия CLI, которую он вызывает; заранее совместимость не предполагать.
   8. Политика статусов: что считается `FAILURE`, что `UNSTABLE` (см. п. 3), кто утверждает.
   9. Если Jenkins или агент недоступны: не выдумывай результаты. Разрешена только статическая проверка синтаксиса `Jenkinsfile`; интеграция помечается **непроверенной**, DoD фазы не считается выполненным.

1. АРХИТЕКТУРА (обосновать и записать в `decisions.md`)
   - **Браузер на агенте (дефолт):** Chrome/Chromium + драйвер из окружения агента, Selenium Manager, headless. Не требовать remote и не поднимать Selenoid/Grid «на всякий случай».
   - **Remote (Selenoid/Grid):** только при подтверждённой необходимости; URL передавать через `withCredentials`, не печатать; передавать тем же ключом, что локально/GHA (`REMOTE` / `-Dselenide.remote`), и подтвердить в логе, что браузер удалённый.
   - **Docker-агент/sidecar:** только если Docker реально доступен агенту (проверено `docker.sock`), иначе вариант не предлагать.
   - `--no-sandbox` не является универсальной настройкой. Допустим только как компромисс конкретного runner (например, Chrome под root в контейнере), с записью причины, риска и области действия; по умолчанию не добавлять.
   - Тесты и локаторы ради Jenkins не менять.

2. JENKINSFILE
   - Declarative pipeline; `agent { label '<согласованный>' }`; при ручном checkout — `skipDefaultCheckout`.
   - Стадии: Checkout → Test → Report → Publish; уведомление — в `post`.
   - `options`: `timestamps()`, `buildDiscarder`, `disableConcurrentBuilds()`, разумный `timeout`.
   - Прогон — **та же команда wrapper**, что локально и в GHA: `./gradlew clean test -Dselenide.headless=true` (на Linux-агенте; на Windows — `gradlew.bat`). `--no-daemon` добавлять только осознанно для CI и зафиксировать; это не новый профиль конфигурации.
   - Те же ключи `-D`/env, что локально и в GHA; никакого «особого jenkins-профиля» и второго источника истины.
   - Ошибку тестов не проглатывать: `catchError(buildResult: 'FAILURE', stageResult: 'FAILURE')` вокруг прогона, чтобы отчёт и публикация выполнились, но сборка осталась красной. `|| true`, `returnStatus` и `currentBuild.result = 'SUCCESS'` для маскировки падения не использовать.
   - Генерация отчёта:
     - **CLI (рекомендуемый, как в CI):** `npx --yes allure@3.33.0 generate build/allure-results --clean`; проверить Node ≥ 22.18 и доступ к npm registry с агента.
     - **Allure plugin:** только если версия плагина и его CLI доказанно совместимы с Allure 3; задать версию явно, сверить в логе фактическую версию CLI, наличие `index.html` в корне output и совпадение `summary.json` с числом тестов. Несовпадение — fallback на закреплённый CLI, а не «подкрутка» версий проекта.
   - Публикация:
     - `junit` по `build/test-results/test/*.xml` — JUnit XML обязателен.
     - Всегда архивировать `build/allure-results/**` (результаты и вложения: скриншоты, page source), `build/test-results/**`, `build/reports/**` и сгенерированный HTML-отчёт.
     - Ссылка на отчёт должна открываться со страницы сборки: `publishHTML`, артефакт или штатная ссылка плагина — по согласованному способу; проверить фактический URL, а не предполагать.
   - `post { always { ... } }` не должен менять итоговый статус сборки; порядок шагов выбрать так, чтобы падение `junit`/публикации не отменяло архивирование и уведомление.

3. JUNIT XML И СТАТУСЫ
   - Публиковать JUnit XML всегда, когда он есть; при падении assertion он обязан появиться.
   - Отсутствие результатов — не «зелёный» сценарий. Проверить и согласовать поведение для двух случаев:
     - ошибка компиляции → XML нет, сборка `FAILURE`, консоль и архив сохранены;
     - тесты не запускались/результаты удалены → явная ошибка или согласованное предупреждение, но не молчаливый успех.
   - `allowEmptyResults` и порядок шагов в `post` выбрать так, чтобы (а) при ошибке компиляции архив и уведомление всё равно выполнились, (б) отсутствие XML не давало зелёную сборку. Оба случая проверить.
   - Рекомендуемая политика (подтвердить у студента):
     - `FAILURE`: упавшие тесты, ошибка компиляции, отсутствие обязательного отчёта/результатов, исключение шага;
     - `UNSTABLE`: только заранее согласованные некритичные условия; по умолчанию не использовать.
   - Не понижать `FAILURE` до `UNSTABLE` и не повышать `UNSTABLE` до `SUCCESS` без явного решения, записанного в `decisions.md`.
   - Учесть, что `post { success }` / `post { failure }` не срабатывают для `UNSTABLE`: если `UNSTABLE` разрешён, уведомление отправлять из `always` по фактическому статусу.

4. УВЕДОМЛЕНИЕ
   - Переиспользовать `.github/scripts/notify-telegram.sh` и тот же текст, что в фазе 5; отличается только доставка credentials.
   - `withCredentials` (Secret text) для token/chat id; значения не печатать, `set -x` не включать; проверить консоль на токен, `chat_id=`, URL API.
   - Отправка при success и failure; при `UNSTABLE` — по согласованной политике из п. 3.
   - Если credentials не заданы — предупреждение и пропуск, сборка не падает. Ошибка Telegram API не должна менять статус тестовой сборки.
   - Ссылка в сообщении — на конкретную сборку и на фактически доступный отчёт; `REPORT_PUBLISHED` выставлять по реальному наличию отчёта, а не по ожиданию.

5. ПРОВЕРКА НА РЕАЛЬНОМ АГЕНТЕ (матрица; результаты — в отчёт)
   1. **Success:** зелёная сборка, JUnit XML опубликован, отчёт открывается со страницы сборки, уведомление доставлено, секретов в консоли нет.
   2. **Падение assertion** (временно): сборка `FAILURE` (не `SUCCESS`/`UNSTABLE` без согласования), JUnit XML содержит упавший тест, в `allure-results` есть вложения (скриншот/page source), отчёт и архив сохранены, уведомление отправлено; затем откат.
   3. **Ошибка компиляции** (временно): сборка `FAILURE`, результатов нет, консоль и архив сохранены, публикация/уведомление не отменены, отсутствие XML не даёт зелёный статус; затем откат.
   4. **Отсутствие результатов** (например, тесты пропущены или каталог очищен): поведение соответствует п. 3, статус не зелёный без явного решения.
   5. **Повторный запуск:** нет залипших контейнеров/портов/сессий; при remote — браузер действительно удалённый, локальный Chrome на агенте не требуется.
   6. **Секреты:** в консоли нет токена, chat id, WebDriver URL с credentials; значения замаскированы.
   - Если Jenkins недоступен: проверить синтаксис `Jenkinsfile` (declarative linter через Jenkins API/`jenkins-cli`, если доступно; иначе — парсинг Groovy) и явно написать «интеграция не проверена». Не выдавать статическую проверку за выполненный DoD.

6. ОТЧЁТ
   - `Jenkinsfile` + список требуемых плагинов с версиями + credentials ID (без значений) + способ запуска браузера.
   - Матрица проверок из п. 5: что запускалось, статус, ссылки, что сохранено.
   - Скриншот/описание страницы сборки с JUnit и Allure.
   - Что отличается от GHA и почему; что осталось общим (команда, ключи, версия CLI).
   - Обнови `decisions.md`: архитектура браузера, способ генерации отчёта, плагины, credentials, политика FAILURE/UNSTABLE, статус фазы, открытые ограничения.

ОГРАНИЧЕНИЯ
- Не устанавливать плагины, не менять глобальную конфигурацию Jenkins, не создавать credentials без разрешения.
- Не менять тесты и локаторы ради Jenkins.
- Не хранить токены, chat id и WebDriver URL с credentials в `Jenkinsfile`, параметрах job или репозитории.
- Не копировать `--no-sandbox` как универсальную настройку.
- Не предполагать совместимость Allure plugin с Allure 3 без проверки.
- Не добавлять шаги «на будущее», которых нет в DoD.
- Не выполнять `git commit`/`git push` без явной команды.

DoD ФАЗЫ
- На реальном агенте: success и контролируемые падения дают ожидаемый статус; падение не замаскировано.
- JUnit XML опубликован; Allure-отчёт доступен из сборки; при падениях сохранены результаты, вложения и отчёт.
- Уведомление приходит при success и failure (или при согласованной политике для `UNSTABLE`).
- Секретов нет в консоли и репозитории.
- Задокументированы плагины и версии, credentials ID, способ запуска браузера, политика FAILURE/UNSTABLE.
- Если Jenkins/агент недоступны — синтаксис проверен, интеграция помечена непроверенной, DoD не закрыт.
