ЗАДАЧА ФАЗЫ 6 — сборка в Jenkins: тесты в контейнере с браузером/драйвером, публикация Allure, уведомление в Telegram.

ПРЕДУСЛОВИЯ
- Прочитай `decisions.md`: версии, команды Allure, ограничения Jenkins Allure plugin по итогам фазы 3.
- Уточни у студента доступное окружение: есть ли Docker Pipeline plugin, агенты с Docker, можно ли использовать Selenium Grid. Без этого не выбирай архитектуру.

1. ВЫБЕРИ ПОДХОД (обоснуй, запиши в `decisions.md`)
   - A. Docker-агент с JDK + установка Chrome в пайплайне: просто, но медленно и хрупко (apt, версии).
   - B. Собственный образ (JDK + Chrome + драйвер), собранный заранее: детерминированно, но нужен registry.
   - C. `selenium/standalone-chrome` как sidecar/сервис в `docker`-агенте + `-Dselenide.remote=http://<host>:4444/wd/hub`: ближе всего к «драйвер в раннере», хорошо масштабируется.
   - Для учебной сборки рекомендуй B или C; A — только если Docker недоступен.

2. JENKINSFILE
   - Declarative pipeline, стадии: Checkout → Test → Allure → Publish → Notify (`post { always { ... } }`).
   - `options`: `timestamps()`, `buildDiscarder`, `disableConcurrentBuilds()`, разумный `timeout`.
   - Прогон: те же команды/ключи, что локально и в GHA. Если используется remote — передавай `-Dselenide.remote` (Selenide читает его сам) и проверь, что браузер реально удалённый (лог/подтверждение).
   - Не дублируй конфигурацию: один источник истины (`-D`/env), без «особого jenkins-профиля».

3. ALLURE В JENKINS
   - Проверь, поддерживает ли установленный Jenkins Allure plugin Allure 3. Если нет — не ломай плагин: генерируй HTML штатной командой Allure 3 в пайплайне и публикуй через `publishHTML` (или archive + ссылка), либо подними статический отчёт.
   - Артефакты: `allure-results` архивируй всегда; HTML — публикуй.
   - Ссылка на отчёт должна быть доступна со страницы сборки.

4. УВЕДОМЛЕНИЕ
   - Используй `withCredentials` (Secret text: токен, chat id) и тот же текст сообщения, что в фазе 5.
   - Отправка в `post { success }` и `post { failure }`; в `post { always }` — публикация артефактов.
   - В консоли не должно быть токена. Не включай `set -x` в шагах с секретами.
   - Если credentials не заданы — шаг пропускается с предупреждением, сборка не падает.

5. ПРОВЕРКА
   - Реальная сборка: зелёная, отчёт открывается из Jenkins.
   - Намеренно упавший тест (временно) → красная сборка, уведомление с корректными ссылками; затем откат.
   - Проверь, что remote-браузер используется (если вариант C) и что локальный Chrome в агенте не требуется.
   - Проверь повторный запуск: нет «залипших» контейнеров/портов.

6. ОТЧЁТ
   - `Jenkinsfile` + список требуемых плагинов и credentials (ID).
   - Скриншот/описание страницы сборки с отчётом.
   - Что отличается от GHA и почему (и что осталось общим).
   - Обнови `decisions.md`: подход, образ/сервис, плагины, credentials, статус фазы.

ОГРАНИЧЕНИЯ
- Не меняй тесты и локаторы ради Jenkins.
- Не храни токены в Jenkinsfile, в job parameters или в репозитории.
- Не добавляй шаги «на будущее», которых нет в DoD.

DoD ФАЗЫ
- Зелёная сборка, отчёт доступен из сборки.
- Уведомление приходит в success и failure.
- Секретов нет в консоли и в репозитории.
- Задокументированы плагины, credentials и способ запуска браузера.
