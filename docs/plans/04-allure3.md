# 04 — Фаза 3: Allure Report 3

| Поле | Значение |
|---|---|
| Модель | Claude Sonnet 5.5 (high) или Gemini 3.1 Pro (high) |
| Reasoning | high — самая «документационная» фаза, легко нагаллюцинировать CLI и версии |
| Зависит от | Фаза 2 (зелёные тесты); вердикт фазы 0 по совместимости адаптера с JUnit 6 |
| Время | ~30–45 мин |
| Артефакты | Адаптер в `build.gradle`, метаданные, шаги/вложения, команда генерации отчёта |
| DoD | Отчёт генерируется одной командой, содержит все тесты, шаги и скриншот при падении |

> Скопируйте всё, что ниже разделителя, в новую сессию (вместе с `00-master-prompt.md`).

---

ЗАДАЧА ФАЗЫ 3 — подключить Allure Report 3 к существующим тестам. Логику тестов и локаторы не меняй.

ПРЕДУСЛОВИЯ
- В `decisions.md` есть вердикт по совместимости адаптера с JUnit Jupiter 6.1.3.
- Если вердикт «несовместимо» — СТОП. Предложи 2–3 варианта (понизить JUnit до поддерживаемой 5.x; другой адаптер; иной генератор) с плюсами/минусами и жди решения. Не понижай версии сам.
- Проверь официальную документацию Allure 3: способ установки CLI, команды генерации, требования к каталогу результатов. Приведи ссылки. Не выдумывай флаги: если команда не подтверждена — пометь «требует проверки» и проверь фактическим запуском.

1. АДАПТЕР И РЕЗУЛЬТАТЫ
   - Добавь адаптер в `build.gradle` (версия — по вердикту фазы 0).
   - Убедись, что результаты пишутся в `build/allure-results` (укажи явно, если дефолт иной).
   - Интеграция Selenide → Allure: проверь, актуален ли `allure-selenide` для Allure 3. Если да — включи скриншот и page source при падении через listener в `TestBase` (согласно S7, без дублирования). Если нет — используй документированный способ Allure 3 и зафиксируй выбор.
   - Никаких скриншотов «на каждый шаг» — только при падении/по необходимости: отчёт не должен раздуваться.

2. МЕТАДАННЫЕ (согласно S10)
   - Если S10 = «обязательны»: `@Epic`, `@Feature`, `@Story`, `@Owner`, `@Severity` — осмысленные, без копипаста одного значения во все тесты.
   - Имена тестов/`@DisplayName` — согласно S9.
   - Не добавляй аннотации, которые не влияют на отчёт (ритуал ради ритуала).

3. ГЕНЕРАЦИЯ ОТЧЁТА
   - Зафиксируй ОДНУ воспроизводимую команду (или пару «generate + open») для локального запуска. Проверь её с чистого состояния: `./gradlew clean test -Dselenide.headless=true`, затем генерация.
   - Если для Allure 3 нужен конфиг-файл — добавь его, минимальный и читаемый.
   - Команды запиши в `decisions.md` и подготовь фрагмент для README (сам README — фаза 7).

4. ПРОВЕРКА ВЛОЖЕНИЙ (контролируемая поломка)
   - Временно сломай один ассерт, прогони тесты, сгенерируй отчёт.
   - Убедись: тест красный, шаги видны, скриншот/page source приложены.
   - Верни ассерт как было, прогони ещё раз — всё зелёное, отчёт чистый.

5. ОТЧЁТ
   - Точные версии адаптера и CLI, ссылки на документацию.
   - Команды: прогон → генерация → просмотр.
   - Что видно в отчёте (список тестов, шаги, вложения) — со скриншотом или описанием.
   - Ограничения для Jenkins (фаза 6): поддерживает ли Allure 3 штатный плагин; если нет — какой fallback.
   - Обнови `decisions.md` (версии, команды, риски), статус фазы.

ОГРАНИЧЕНИЯ
- Не меняй набор тестов и их логику (кроме временной контролируемой поломки, которую обязан откатить).
- Не обновляй JUnit/Gradle без согласования.
- Не коммить `build/` и сгенерированный отчёт.

DoD ФАЗЫ
- `build/allure-results` наполняется при прогоне.
- Отчёт генерируется документированной командой, открывается в браузере.
- В отчёте: все тесты, шаги, вложение при падении (проверено контролируемой поломкой и откатом).
- Команды и версии зафиксированы в `decisions.md`.
